# 0013. 프로젝트 진행률을 태스크에서 계산한다

- 상태: Accepted
- 날짜: 2026-07-17
- 작성자: 신진수

## 맥락

브리프는 프로젝트 스냅샷에 진행률을 함께 내려준다. 현재 서버는 `projects.progress` 컬럼을 그대로 반환하지만, 이 값을
갱신하는 주체가 없다. 그 결과 화면의 진행률이 실제 태스크 상태와 쉽게 어긋난다. 현재 dev DB에서도 저장된 진행률은
64지만 실제 태스크는 83건 중 done이 2건뿐이다.

레거시 `momens-api`도 이 컬럼을 계산하지 않는다. `progress`는 클라이언트가 보낸 값을 0~100 범위인지 확인한 뒤 그대로
저장하는 수동 입력 컬럼이며(`internal/project/service.go`의 `normalizeProgress`), 태스크 상태가 바뀌어도 진행률을
다시 계산하지 않는다. 트리거나 뷰도 없다. 레거시를 그대로 따르려 해도 계산 기준으로 삼을 원본이 없다.

계산 규칙의 출처는 2026-06-24 기획 회의 ADR 하나다.

> 진행률은 '프로젝트에 연결된 전체 task 수' 대비 'done 상태인 task 수'로 계산한다.

다만 해당 ADR은 다음 항목을 후속 과제로 남겼다.

> (Follow-ups) 백엔드와 진행률 계산 방식(완료 상태 정의, 연결된 task 기준) 정합성 확인 및 API 명세 업데이트.

따라서 이번 ADR에서는 다음 세 가지를 결정한다.

1. 진행률을 저장할지, 조회 시 계산할지
2. 진행률 계산 대상에 어떤 상태를 포함할지
3. 소수점을 어떻게 처리할지

## 결정

진행률은 저장하지 않고 조회 시 태스크 상태를 기준으로 계산한다. 계산은 `project` 모듈이 담당하며
`ProjectReader.progressOf`로 공개한다. 브리프는 계산 결과만 받아 사용한다.

- **저장하지 않고 계산한다.** 태스크 상태는 done에서 다시 todo로 되돌릴 수 있다. 저장 컬럼을 유지하면 증가와 감소
  경로를 모두 관리해야 하고, 하나라도 빠지면 값이 영구히 어긋난다. 현재 dev DB의 진행률 64도 이런 상태다. 조회 시
  계산하면 별도의 갱신 경로가 없어 값이 누적해서 어긋날 수 없다.
- **집계 쿼리를 별도로 만들지 않는다.** `TaskReader.listTasksByStatus`가 반환한 동일한 조회 결과에서 전체 태스크 수와
  done 태스크 수를 함께 계산한다. 별도 집계 쿼리를 두면 목록 조회와 계산 기준이 달라질 수 있다. MOM-0779에서
  `material_count`가 같은 이유로 어긋나 `count ... group by`를 제거했던 경험을 그대로 따른다.
- **cancelled를 제외한다(기획 확정).** 06-24 ADR 문구를 그대로 해석하면 cancelled도 전체 태스크에 포함되지만, 그러면
  취소한 태스크가 진행률을 영구히 낮춰 남은 태스크를 모두 완료해도 진행률이 100이 될 수 없다. 취소한 태스크는 더 이상
  진행 대상이 아니므로 계산에서 제외한다. 이 해석은 기획이 확정했다(2026-07-17 구두 확인).
  구현은 계산 단계에서 제외하는 대신 조회 대상에 cancelled를 포함하지 않는 방식을
  사용한다. 조회 대상은 상태를 개별적으로 나열하지 않고 `TaskStatus` 전체에서 cancelled만 제외해 계산한다. 상태를
  나열하면 새 상태가 추가되더라도 문서는 여전히 "cancelled 제외"로 읽히지만, 구현에는 반영되지 않을 수 있다. 그 결과
  새 상태가 계산 대상에서 빠져 실제보다 높은 진행률이 계산될 수 있다.
- **소수점은 버린다.** 정수 나눗셈으로 계산한다. 반올림하면 199/200이 99.5%여도 100이 되어 미완료 태스크가 남은
  상태에서 완료로 보인다. 소수점을 버리면 100은 cancelled를 제외한 모든 태스크가 done인 경우만 의미한다.
- **소프트 삭제된 태스크는 제외하고, 태스크가 없으면 0을 반환한다.** 보드 조회와 같은 기준을 사용한다.
- **`projects.progress` 컬럼은 유지하고 매핑만 제거한다.** 레거시 웹은 여전히 이 컬럼을 수동으로 사용하고 있으며 운영
  공유 스키마는 레거시가 관리한다. 매핑을 제거해도 `ddl-auto=validate`는 영향을 받지 않는다. `Project` 엔티티 역시
  이미 `health_status`, `unresolved_count`, `metadata` 등을 매핑하지 않고 있으며, validate는 매핑된 컬럼만 검증한다.

## 대안

- **저장 컬럼을 서버가 갱신한다.** 태스크 상태가 바뀔 때마다 `projects.progress`를 갱신한다. 조회 비용은 줄지만 쓰기
  경로 하나라도 빠지면 값이 영구히 어긋난다. 모바일 DB는 웹과 분리 운영 중이라 조회 시 계산해도 레거시 웹의 수동
  입력과 충돌하지 않는다.
- **`count ... group by` 집계 쿼리를 사용한다.** 조회는 단순해지지만 목록 조회와 계산 기준이 달라질 수 있다. 이미
  MOM-0779에서 제거한 방식이다.
- **Hibernate `@Formula`를 사용한다.** 매핑은 단순해지지만 진행률이 필요 없는 조회까지 항상 서브쿼리를 수행한다. 현재
  레포에도 `@Formula` 사용 사례가 없다.
- **mobile에서 계산한다.** 브리프가 조회한 태스크를 우선순위와 진행률 계산에 함께 사용할 수 있다. 하지만 진행률 계산
  정책이 mobile 계층으로 퍼지고, 다른 표면에서도 같은 정책을 중복 구현해야 한다. 계산 기준은 project 모듈이 담당하는
  것이 맞다.
- **`ProjectSnapshot`에 계산값을 포함한다.** 변경 범위는 작지만 `findSnapshot`만 계산하면 `listByWorkspaceIds`와
  결과가 달라지고, 두 경로 모두 계산하면 bootstrap에서도 사용하지 않는 진행률 때문에 프로젝트마다 태스크를 모두
  조회하게 된다.

## 결과

- 브리프 진행률은 항상 현재 태스크 상태를 반영한다. 완료를 되돌리면 다음 조회부터 즉시 감소한다.
- 브리프 한 요청에서 태스크를 두 번 조회한다. 하나는 우선순위(todo, in_progress) 계산용이고, 다른 하나는
  진행률(cancelled 제외) 계산용이다. 계산 정책을 mobile로 옮기지 않는 대신 조회를 분리한다. signal도 개수와 목록 계산
  때문에 같은 행을 두 번 조회하고 있어 같은 수준의 비용이다.
- cancelled 제외는 기획이 확정했다(2026-07-17 구두 확인). 2026-06-24 ADR의 follow-up인 "완료 상태 정의, 연결된 task
  기준" 정합성 확인이 이것으로 닫힌다. 다만 확정 근거가 구두라 제품 원장(Notion)에 기록이 남아야 하고, teams ADR은
  Notion에서 생성되므로 그 기록이 들어와야 여기 인용을 갱신할 수 있다.
- 소수점 버림은 아직 기획 확정 사항이 아니라 서버 구현에서 결정한 정책이다. 기획과 공유해 확정 결과에 따라 변경한다.
- 진행률 표시가 크게 달라질 수 있다. 현재 dev 데이터에서는 64에서 2로 변경되므로 데모 전에 현실적인 완료 비율로
  데이터를 다시 구성할 필요가 있다.
- `projects.progress`는 이 서버에서 읽지도 쓰지도 않는 레거시 컬럼으로 유지한다. 웹 이관 시 진행률 정책과 함께 다시
  검토한다.
