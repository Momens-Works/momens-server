# 0003. 인증 세션·전송 모델: 모바일/웹 하이브리드

- 상태: Accepted
- 날짜: 2026-06-25
- 작성자: Kimgyuilli

## 맥락

`momens-server`는 레거시 Go `momens-api`를 대체하며 모바일(신규 네이티브 앱)과 웹을 모두
인증해야 한다. 인증 코어(MOM-8)를 세우며 토큰 전송수단과 세션 수명 모델을 확정해야 했다.

- 모바일은 푸시 기반 네이티브 앱이라 네이티브 Google Sign-In(ID 토큰) + Authorization
  헤더(Bearer)가 자연스럽다.
- 웹은 `momens-fe`가 단독 소유(TL)이고, 레거시는 단일 세션 쿠키를 써 왔다.
- 핵심 미결정은 웹 토큰 수명이었다: **레거시 호환 단일 세션 쿠키** vs **access+refresh
  현대화**. 이 선택은 권한 변경 반영 속도·세션 강제 종료·토큰 탈취 대응에 직접 영향을 준다.

`momens-fe` TL과 협의해 방향을 확정했다.

## 결정

**플랫폼 중립 코어 위에 전송수단만 분리하는 하이브리드**로 한다.

1. **세션 모델은 공통 access + refresh** 단일 체계로 모바일·웹이 공유한다(레거시 단일 세션
   쿠키는 폐기).
2. **전송수단만 플랫폼별로 분리**: 모바일=Authorization Bearer, 웹=HttpOnly 쿠키(+ 교차
   도메인 시 CSRF 토큰).
3. **refresh는 회전**하고 서버에 저장한다. access는 단명으로 둬 변경된 권한의 stale 상한을
   짧게 한다.
4. 코어는 플랫폼 중립으로 설계한다: JWT 클레임에 전송수단 정보를 넣지 않고(sub=userId 최소),
   refresh store에 client_type/device 필드를 두며, 필터 체인에 쿠키 추출·CSRF seam을 남긴다.
5. **모바일을 먼저 구현**(코어를 가장 단순한 Bearer로 검증)하고, 웹은 같은 코어에
   `BearerTokenResolver` 교체 + CSRF 재활성화로 얹는다(MOM-22).

## 대안

- **레거시 호환 단일 세션 쿠키 유지**: 컷오버는 단순하지만 access+refresh의 이점(권한 변경의
  빠른 반영, 세션 강제 종료, refresh 회전으로 탈취 대응, 모바일과 단일 세션 체계)을 포기한다.
  모바일에 별도 토큰 체계가 또 필요해 이중화된다. 기각.
- **웹도 Bearer(헤더) 토큰**: 웹에서 토큰을 JS가 들고 있어야 해 XSS 노출면이 커지고 HttpOnly
  보호를 못 쓴다. 기각.
- **모바일/웹 각각 독립 세션 체계**: 단순해 보이나 폐기·회전·저장 로직이 둘로 갈려 유지보수와
  보안 점검이 배가된다. 기각.

## 결과

- 세션 체계가 하나라 refresh 회전·폐기·저장 로직을 한 곳에서 관리한다.
- 웹은 `momens-fe`에 자동 재발급·CSRF·로그아웃 토큰 정리 작업이 추가되어 서버와 동시 배포가
  필요하다(MOM-22).
- access가 단명이라 권한 변경은 "즉시"가 아니라 access TTL 안에서 반영된다(stale 상한). 진짜
  즉시 폐기가 필요하면 refresh 회수에 의존한다 — 단, refresh 폐기는 모바일에 한정되므로(R1)
  "세션 폐기 의존 기능"을 계약으로 약속하지 않는다.
- 웹 컷오버 전까지는 웹이 레거시 `momens-api`와 병행 운영될 수 있다(R6).
- 이 모델을 구현하는 토큰 발급·검증 스택은 [ADR-0004](0004-token-issuance-verification-stack.md)에서 정한다.
