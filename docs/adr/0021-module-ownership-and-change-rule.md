# 0021. 모듈별 담당 영역 배정 및 공용 모듈 변경 규칙

* 상태: Proposed
* 날짜: 2026-09-01
* 작성자: jsshin8128

## 맥락

2026-08-27부터 서버 담당 영역을 웹과 모바일로 분리했습니다. 그러나 각 모듈의 담당 영역이 정해져 있지 않아 다음 두 가지를 판단하기 어려운 상황입니다.

* 모바일 서버의 기술 부채를 어디까지 조사할 것인가
* 웹과 모바일이 함께 사용하는 모듈을 변경할 때 작업 범위를 어디까지로 볼 것인가

`docs/design/module-map.md`에는 각 모듈의 책임만 정의되어 있고 담당 영역은 명시되어 있지 않습니다. 현재 담당 영역을 판단할 수 있는 근거는 `build.gradle`에 정의된 모듈 간 의존 관계가 유일합니다. 이 정보로 어떤 모듈이 해당 모듈을 참조하는지는 확인할 수 있지만, 어느 영역에서 관리하는지는 알 수 없습니다.

처음에는 각 모듈에 대상 클라이언트를 지정하는 방식을 검토했습니다. 그러나 이 방식은 채택하지 않았으며, 그 이유는 아래 대안 절에 정리합니다.

## 결정

**모든 모듈에 담당 영역을 지정하고, 웹과 모바일이 공동으로 담당하는 모듈을 변경할 때는 합의 절차를 적용합니다.**

담당 영역은 **해당 모듈의 비즈니스 규칙을 변경하는 영역**을 기준으로 지정합니다. 모듈을 읽기 전용으로 참조하는 영역은 해당 모듈을 변경하기 전에 협의해야 하는 대상으로 봅니다.

이 기준을 선택한 근거는 세 가지입니다.

첫째, Eric Evans의 Shared Kernel 패턴을 따릅니다. 패턴 원칙에 따라, 두 영역이 공유하는 모델을 상대 영역과 협의 없이 변경하지 않고, 공유 범위를 작게 유지하도록 합니다. 웹과 모바일이 공동으로 담당하는 모듈이 이에 해당합니다.

둘째, 모듈러 모놀리스의 소유권 원칙에 따라 각 팀이 모듈의 코드, 스키마, public API를 소유하도록 정하고 있습니다. 동시에 **공동 소유는 대개 소유권 부재로 이어진다**고 경고합니다. 따라서 담당 영역이 없는 모듈이 생기지 않도록 모든 모듈에 담당 영역을 명시해야 합니다.

셋째, 현재 각 모듈을 담당하는 비즈니스 기능과 규칙에 따라 모듈을 나누고 있습니다. 따라서 해당 비즈니스 규칙을 변경하는 주체를 담당 영역으로 지정하는 것이 기존 모듈 분할 기준과도 일치합니다.

담당 영역은 담당자가 바뀔 때마다 문서를 수정하지 않도록 개인 이름이 아닌 영역으로 관리합니다.

| 담당 영역        | 모듈                                                                |
| ------------ | ----------------------------------------------------------------- |
| 모바일 서버       | `mobile`, `minsu`, `notification`, `signal`                       |
| 웹 서버         | `web`, `memory`, `onboarding`, `context`, `source`, `workspace`   |
| 웹 서버와 모바일 서버 | `app`, `common`, `project`, `user`, `auth`, `outbox`             |

**웹과 모바일이 공동으로 담당하는 모듈의 public API와 스키마는 상대 영역과 협의 없이 변경하지 않습니다.** `internal` 패키지는 다른 모듈에서 참조할 수 없으므로 이 규칙을 적용하지 않습니다. `app`은 다른 모듈에서 참조하지 않고 마이그레이션도 소유하지 않으므로 이 규칙의 대상에서 제외합니다.

**담당 영역이 하나인 모듈이라도 상대 영역에서 읽기 전용으로 참조한다면 해당 타입의 시그니처를 변경하기 전에 상대 영역에 알립니다.** `workspace`의 `WorkspaceAccess`, `context`의 `EntityRelationReader`, `source`의 `SourceRefReader`가 이에 해당합니다.

**새 모듈을 만들 때는 담당 영역도 함께 지정합니다.** 담당 영역 열만 표에 추가하고 모듈 생성 절차에는 포함하지 않으면 이후 추가되는 모듈의 담당 영역이 누락될 수 있습니다.

**기술 부채 조사 범위를 담당 영역만으로 제한하지 않습니다.** 조사는 해당 클라이언트 모듈이 직접 호출하는 public API와 그 구현에서 시작합니다. 담당 영역은 조사 과정에서 발견한 기술 부채를 누가 어떤 방식으로 처리할지 판단하는 기준으로 사용합니다.

* 모바일 담당 모듈에서 발견한 기술 부채는 모바일 담당 영역에서 직접 수정합니다.
* 웹과 모바일이 공동으로 담당하는 모듈에서 발견한 기술 부채는 협의한 뒤 수정합니다.
* 웹 담당 모듈에서 발견한 기술 부채는 웹 담당 영역에 알리고, 처리 여부는 웹 담당 영역에서 결정합니다.

조사 시작점은 해당 클라이언트 모듈의 소스가 참조하는 다른 모듈의 public 타입을 추출해 정합니다. **같은 기준을 웹 서버에도 적용합니다.** `modules/web`에서 참조하는 public 타입을 시작점으로 삼고, 처리 기준에서 모바일과 웹의 역할을 바꾸면 같은 방식으로 적용할 수 있습니다.

## 대안

**각 모듈에 대상 클라이언트를 지정하는 방식은 채택하지 않았습니다.** BFF는 웹과 모바일 클라이언트로부터 내부 모듈을 감추고, 도메인 모듈이 특정 클라이언트에 종속되지 않도록 유지합니다. `mobile`과 `web`을 별도의 진입 모듈로 둔 이유도 여기에 있습니다. 하위 모듈에 다시 대상 클라이언트를 지정하면 동일한 정보를 두 계층에서 중복하여 관리하게 됩니다.

실측 결과 웹과 모바일이 함께 참조하는 모듈이 도메인 소스의 65%를 차지합니다. 따라서 이 기준만으로는 기술 부채 조사 범위를 충분히 좁히기 어렵습니다. 또한 진입점이 웹과 모바일에만 한정되는 것 또한 아닙니다.

**`CODEOWNERS` 도입은 이번 작업 범위에서 제외했습니다.** 모듈 메타데이터에서 `CODEOWNERS`를 자동으로 생성하는 장치 없이 도입하면 동일한 정보를 두 곳에서 수동으로 관리해야 하므로 서로 불일치할 수 있습니다. Spring Modulith의 Application Module Canvas는 항목을 추가하거나 제거하는 기능을 제공하지 않으므로, 코드에 담당 영역 정보를 추가해 자동 생성하는 방식도 사용할 수 없습니다. 현재는 팀원이 두 명이고 서로 리뷰하고 있으므로 리뷰어를 자동 지정하는 이점도 크지 않습니다.

## 결과

담당 영역이 문서에 명시되므로 모듈을 변경할 때 누구와 협의해야 하는지 확인할 수 있습니다. 기술 부채를 조사할 때도 어디에서 시작하고, 발견한 부채를 어느 영역에서 처리해야 하는지 판단할 수 있습니다.

**합의 규칙을 위해 별도의 절차를 추가하지 않습니다.** 두 ruleset에서 한 명의 승인을 요구하고 현재 팀이 두 명으로 구성되어 있으므로, 웹과 모바일이 공동으로 담당하는 모듈을 변경하면 상대 영역 담당자가 자연스럽게 리뷰어가 됩니다.

**모듈별 담당 영역 표는 수동으로 관리합니다.** 자동 생성 장치가 없으므로 모듈을 추가할 때마다 담당 영역을 입력해야 합니다. 누락을 방지하기 위해 모듈 생성 절차에 담당 영역 지정 작업을 포함합니다.

**웹과 모바일이 공동으로 담당하는 모듈의 수가 늘어나거나 해당 모듈의 외부 공개 범위가 확대되면 모듈 경계를 다시 검토합니다.** 담당 영역을 하나로 명확하게 나누기 어렵다는 것은 해당 모듈이 서로 다른 책임을 함께 수행하고 있다는 신호일 수 있습니다.
