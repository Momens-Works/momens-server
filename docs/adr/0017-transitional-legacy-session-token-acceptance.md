# 0017. 전환기 레거시 `session_token` 한시 수용

- 상태: Accepted
- 날짜: 2026-08-17
- 작성자: Kimgyuilli

## 맥락

첫 웹 read 수직 슬라이스(`MOM-0850`, `MOM-0851`)는 레거시 `GET /workspaces`,
`GET /workspaces/:id`를 `momens-server`로 옮긴다. 이때 인증이 끊긴다.

- 운영 웹은 레거시 `momens-api`의 OAuth로 로그인해 `session_token` 쿠키만 갖는다.
  신규 서버의 `access_token` 쿠키는 발급되지 않는다.
- 신규 서버의 `BearerTokenResolver`는 `Authorization` 헤더와 `access_token` 쿠키만 본다.
  따라서 이 상태로 전환하면 신규 endpoint 호출이 `401`을 받는다.

[이관 전략](../design/legacy-product-api-migration-strategy.md)은 이 상태를 혼합 트래픽으로
정의하고 호환 방식 세 가지 중 하나를 명시적으로 고르도록 규정한다. 이 결정은 웹 세션 쿠키를
폐기하기로 한 [ADR-0003](0003-auth-session-transport-model.md)의 한시적 예외이므로 별도 기록이
필요하다.

전환 준비 상태로 확인한 사실은 다음과 같다.

- 두 서버의 토큰이 구조적으로 같다. 모두 HS256이고 claim은 `sub`(userId), `iat`, `exp`뿐이며
  `iss`/`aud`를 쓰지도 검증하지도 않는다.
- 배포 매니페스트가 이미 이 방식을 전제로 두 서버에 같은 서명 키를 주도록 구성돼 있다
  (`k8s/manifests/apps/momens-server/deployment.yaml`의 `MOMENS_AUTH_JWT_SECRET`, transition
  invariant 주석).
- 그 결과 지금도 레거시 토큰 값을 `Authorization` 헤더에 담으면 신규 서버 인증을 통과한다.
  즉 "레거시 토큰을 받지 않는다"는 서술은 현재 배포 구성에서 실효가 없다.

## 결정

**신규 서버가 전환기 동안 레거시 `session_token` 쿠키를 access token으로 수용한다**
(이관 전략의 호환 방식 1).

1. `BearerTokenResolver`에 fallback 한 단계를 더한다. 조회 순서는
   `Authorization` 헤더 → `access_token` 쿠키 → `session_token` 쿠키다.
2. 디코더와 검증은 바꾸지 않는다. 같은 서명 키와 같은 claim을 쓰므로 기존 HS256 디코더가
   그대로 검증한다.
3. 서명 키는 분리하지 않는다. 분리하면 디코더가 둘로 갈리고, 이 결정의 이점인 최소 변경이
   사라진다. 레거시 폐기 시점에 함께 정리한다.
4. 적용 범위는 보호 API 전체다. resolver가 전역이라 웹 표면에만 적용할 수 없다.
5. **제거 조건**: 웹 로그인이 신규 서버(`/api/auth/google/*`)로 전환되어 모든 웹 세션이
   `access_token` 쿠키를 갖게 되면 fallback을 제거한다. 제거는 레거시 `momens-api` 종료와
   묶지 않는다. 웹 로그인 전환만으로 조건이 충족된다.

## 대안

- **웹 로그인을 먼저 신규 서버로 전환한다**: 계약이 깨끗하고 한시적 코드가 생기지 않는다.
  그러나 첫 read 슬라이스가 인증 전환과 묶여, 가장 작은 범위로 시작해 라우팅으로 되돌린다는
  전제가 무너진다. 로그인은 되돌리기 가장 어려운 지점이라 첫 전환 대상으로 두지 않는다. 기각.
- **레거시 서버가 신규 access token을 신뢰한다**(호환 방식 2): 필요한 패치이지만 방향이
  반대다. 신규 토큰을 든 클라이언트가 레거시 endpoint를 호출하는 경우를 풀 뿐, 레거시 세션을
  든 브라우저가 신규 endpoint를 호출하는 이 문제를 풀지 못한다. 별개 작업으로 남긴다.
- **로그인 과정이 두 서버의 세션을 함께 만든다**(호환 방식 3): 로그인 흐름을 전환기 전용으로
  바꿔야 해 변경 범위가 가장 크고, 되돌릴 때도 로그인을 건드린다. 기각.
- **서명 키를 분리하고 레거시 토큰 전용 디코더를 둔다**: 두 토큰을 구조적으로 구분할 수 있다.
  그러나 키 교체 운영이 전환기 한복판에 추가되고, 구분해서 얻는 이득이 지금은 없다. 레거시
  토큰과 신규 토큰의 신뢰 수준이 같기 때문이다. 기각.

## 결과

- 웹 로그인 전환과 무관하게 read 슬라이스를 독립적으로 전환하고 되돌릴 수 있다.
- 한 번 로그인한 세션으로 두 서버를 함께 쓸 수 있어, 이관을 endpoint 단위로 잘게 나눌 수 있다.
- 신규 서버가 레거시 쿠키 이름을 알게 된다. 제거 조건을 명시했지만 관리하지 않으면 남는 부채다.
- **두 토큰을 구조적으로 구분할 수 없다.** 같은 키와 같은 claim을 쓰므로 신규 서버는 요청이
  레거시 세션에서 왔는지 신규 세션에서 왔는지 알 수 없다. 전환 관측이 필요하면 토큰이 아니라
  쿠키 이름(어느 fallback 단계에서 해석됐는지)으로 지표를 남긴다.
- 레거시 세션의 수명은 레거시 서버가 정한다. 신규 서버의 access TTL 정책이 이 토큰에는
  적용되지 않는다.
- ADR-0003의 "레거시 단일 세션 쿠키 폐기"는 유지된다. 이 ADR은 폐기 시점까지의 수용을 정할 뿐
  세션 모델을 되돌리지 않는다.
