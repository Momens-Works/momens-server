# 0021. 엔드포인트 operationId 명명 규칙

- 상태: Proposed
- 날짜: 2026-09-02
- 작성자: jsshin8128

## 맥락

`operationId`는 OpenAPI 문서에서 각 엔드포인트를 식별하는 이름입니다. 값을 지정하지 않으면 springdoc이 컨트롤러 메서드명을 기준으로 자동 생성하며, 같은 이름이 중복되면 뒤에 `_1`을 붙입니다. 번호가 붙는 엔드포인트는 컨트롤러 탐색 순서에 따라 달라지므로, 다른 작업으로 인해 수정하지 않은 엔드포인트의 이름까지 변경될 수 있습니다. 실제로 `MOM-0897`에서 `WorkspaceController`에 메서드 하나를 추가하자 워크스페이스 목록과 초대 목록의 `operationId`가 서로 바뀐 사례가 있었습니다.

springdoc은 이 동작을 비활성화하는 설정을 제공하지 않습니다. 중복 제거는 `OperationIdCustomizer`가 생성된 문서를 순회하면서 수행하며, 이 빈은 `@ConditionalOnMissingBean(name = "globalOpenApiCustomizer")` 조건에 따라 등록됩니다. 따라서 springdoc이 제공하는 범위에서 이름을 고정하려면 각 엔드포인트에 `operationId`를 직접 지정해야 합니다.

`operationId`는 OpenAPI 스냅샷과 클라이언트 코드 생성에 사용됩니다.

* `docs/spec/openapi.json` 스냅샷에 포함됩니다.
* `momens-fe`에 openapi-typescript를 도입하면 `operations` 인터페이스의 키로 사용되어 생성되는 타입명에 반영됩니다.
* `momens-android`는 현재 OpenAPI 명세를 기반으로 코드를 생성하지 않고 경로를 직접 작성합니다. 다만 향후 Kotlin 코드 생성기를 도입하면 동일한 `operationId`를 기준으로 코드를 생성하게 됩니다.

따라서 `operationId`를 직접 지정하려면 특정 클라이언트에 종속되지 않으면서 웹과 모바일에 공통으로 적용할 수 있는 명명 기준이 필요합니다. 그러나 현재는 명명 기준이 문서화되어 있지 않고, 이미 명시된 26개의 `operationId`도 통일된 규칙 없이 작성되어 있습니다.

명명 규칙이 필요한 경우가 하나 더 있습니다. 웹과 모바일이 동일한 자원에 대해 각각 엔드포인트를 제공하는 경우입니다. `PATCH /api/tasks/{taskId}`와 `PATCH /api/mobile/tasks/{taskId}`가 이에 해당하며, 두 엔드포인트는 요청 본문도 서로 다릅니다. OpenAPI 명세에서는 `operationId`가 문서 전체에서 고유해야 하므로, 두 엔드포인트의 이름을 구분할 기준이 필요합니다.

## 결정

**모든 엔드포인트에 `operationId`를 명시하고, 다음 다섯 가지 규칙에 따라 이름을 정합니다.**

1. `<동사><대상>` 형식의 camelCase를 사용하며, OpenAPI 문서 전체에서 고유한 이름을 지정합니다.
2. 목록 조회에는 `list`, 단건 조회에는 `get`, 생성에는 `create`, 수정에는 `update`, 삭제에는 `delete`를 사용합니다. 다만 적절한 도메인 동사가 있으면 해당 동사를 우선합니다.
3. 경로에서 클라이언트를 구분하는 경우 해당 경로 세그먼트를 접두사로 사용합니다. `/api/mobile/**`에는 `mobile`, `/api/auth/web/**`에는 `web`, `/api/dev/**`와 `/api/auth/dev/**`에는 `dev`를 붙입니다. 클라이언트를 구분하는 세그먼트가 없는 `/api/**`에는 접두사를 붙이지 않습니다.
4. 접두사는 경로에서만 가져오며, 모듈명이나 클래스명에서는 가져오지 않습니다.
5. 상위 자원은 문서에서 대상을 식별하는 데 필요한 범위까지만 이름에 포함합니다.

규칙 3에서 클라이언트 구분자를 접두사로 사용하는 이유는 이를 대상의 수식어로 배치하면 의미가 달라질 수 있기 때문입니다. 일례로, `convertMobileSignalToTask`는 시그널이 모바일 전용이라는 의미로 해석될 수 있지만, 실제로는 모바일 앱이 사용하는 경로를 통해 시그널을 태스크로 전환한다는 뜻입니다. 클라이언트 구분자를 접두사로 두면 대상의 속성이 아니라 경로의 네임스페이스로 해석할 수 있습니다.

규칙 3에 따라 `/api/auth/web/**`에는 `web` 접두사를 붙이지만, 나머지 웹 경로에는 접두사를 붙이지 않습니다. 이는 현재 경로 구조상 웹 경로 중 `/api/auth/web/**`만 클라이언트 구분 세그먼트를 포함하기 때문에 발생하는 비대칭입니다. 명명 규칙에서는 이 비대칭이 적절한지 별도로 판단하지 않고 현재 경로를 그대로 따릅니다. 이후 경로를 정리할 때는 명명 규칙을 변경하지 않고, 정리된 경로에 맞춰 `operationId`를 변경할 수 있습니다.

중복이 발생한 경우에만 접두사를 붙이지 않고 해당 경로의 모든 엔드포인트에 일관되게 적용하는 이유는 이름을 처음부터 고정하기 위해서입니다. 중복이 발생했을 때만 접두사를 붙이면 나중에 웹에서 같은 자원을 제공할 때 이미 공개된 모바일 엔드포인트의 이름을 변경해야 합니다. 이 이름은 클라이언트에서 생성되는 타입명으로도 사용되므로 변경 비용이 서버 외부로 전파됩니다.

## 대안

**kebab-case를 사용하는 방안은 채택하지 않았습니다.** Spectral의 기본 규칙은 `lower-hyphen-case`를 권장하지만, 이는 문서 도구에서 `operationId`를 URL로 사용하는 경우를 전제로 합니다. 이 프로젝트에서는 웹과 모바일의 클라이언트 코드 생성기가 `operationId`를 사용합니다. camelCase는 TypeScript와 Kotlin에서 모두 유효한 식별자이므로 명세에 정의된 이름을 코드에서도 그대로 사용할 수 있습니다. 반면 kebab-case는 두 언어 모두에서 식별자로 사용할 수 없어 코드 생성기가 이름을 별도로 변환해야 하며, 일부 생성기는 이러한 변환을 지원하지 않습니다. OpenAPI 명세에서도 일반적인 프로그래밍 언어의 명명 규칙을 따르도록 권장하고 있으며, 이미 명시된 26개의 `operationId`도 camelCase를 사용합니다.

**모듈명을 접두사로 사용하는 방안은 채택하지 않았습니다.** 접두사가 없는 `/api/**`는 현재 이관 중인 레거시 Product API입니다. 현재 웹에서만 호출한다는 사실과 관계없이 경로 자체는 특정 클라이언트로 한정되지 않습니다. 모듈명을 기준으로 접두사를 붙이면 외부 계약에 없는 클라이언트 구분이 추가되며, 이후 모바일에서 해당 경로를 호출할 경우 이름이 실제 사용 방식과 어긋나게 됩니다.

**`OperationCustomizer`로 클래스명과 메서드명에서 이름을 파생하는 방안은 채택하지 않았습니다.** 내부 패키지 구조가 외부 계약에 노출되고, 컨트롤러를 이동하거나 이름을 변경할 때 외부 계약까지 함께 변경되기 때문입니다.

**springdoc의 `globalOpenApiCustomizer` 빈을 교체하는 방안은 채택하지 않았습니다.** 문서 명명 규칙을 적용하려면 애플리케이션 설정까지 변경해야 하고, 특정 빈 이름에 의존하게 됩니다. 이후 springdoc이 해당 이름을 변경하면 별도의 실패 신호 없이 기존 자동 생성 방식으로 되돌아갈 수 있습니다.

## 결과

새 엔드포인트를 추가할 때는 `operationId`를 직접 지정해야 하며, 명명 기준은 이 문서와 `docs/spec/openapi.md`에서 관리합니다. 이름이 고정되므로 엔드포인트를 추가하더라도 기존 엔드포인트의 이름은 변경되지 않습니다. 따라서 OpenAPI 스냅샷 diff에는 실제로 변경한 계약만 나타납니다.

명명 규칙은 특정 클라이언트에 종속되지 않습니다. 따라서 향후 모바일에서 OpenAPI 명세 기반 코드 생성을 도입하더라도 이름을 다시 정할 필요가 없으며, 웹과 모바일 모두 같은 기준으로 생성된 이름을 사용하게 됩니다.

기존에 `operationId`를 명시한 엔드포인트 26개 중 변경 대상은 `updateWebTask` 하나입니다. 나머지는 모두 접두사가 없는 `/api/**` 경로에 속하므로 현재 규칙을 이미 충족합니다.

규칙 준수 여부는 후속 티켓 `MOM-0913`에서 추가하는 검사로 확인합니다. 이 문서에서는 명명 규칙만 정의하며 검사 구현은 다루지 않습니다.
